# Company support integration

The authenticated Work OS frontend has native Support and Knowledge modules. The existing support pilot remains the only Zoho/Grok dispatcher; it is not yet migrated off the Mac. The outbound connector is read-only locally and writes bounded snapshots to PostgreSQL. It never exports credential files, raw mail snapshots, delivery payloads, approval keys or customer-send capabilities.

## Knowledge center / Wiki

The primary Knowledge center / Wiki view embeds the complete public site at `/wiki/`, packaged independently from `Yonge6/onelaser-support-center` at the full commit in `deploy/wiki-revision.txt`. Its homepage, product navigation, full-text search, downloads, article layout, images, original-source links, mobile navigation and language switch are preserved. The original GitHub Pages site remains unchanged and available through the open-original-site action. Updates are reviewed and pinned explicitly, not pulled from a moving branch at runtime.

`tools/fetch-wiki.mjs` accepts only the 259 known public files, including all 236 articles, bounded by individual/total sizes. Every original download must match its Git blob SHA-1 and declared size before packaging. It rejects symlinks, unknown paths, missing articles, inconsistent search indexes, private-operation flags and published/approved states. Docker copies the result to `/app/wiki`; it does not copy any private working tree or credential directory. `wiki-build-info.json` records the source revision and two declared patches: catalog-family input validation in `app.js` and language-preserving internal navigation in `locale.js`. Both are applied only after original blob validation; the other 257 source files retain their exact original bytes. Home (`/`) and hash routes (`/#...`) retain `?lang=zh/en`, so search, products, downloads, article anchors and returning home navigate within the current document. Asset/data revision parameters and external URLs retain their original behavior.

The frame receives only the UI language (`lang=zh` or `lang=en`), with no token in the URL or message bridge. The fixed public code reads local static JSON and does not call employee APIs. Because the frame is now same-origin, its sandbox with scripts and same-origin enabled is **not an isolation boundary**: the reviewed scripts are trusted application code, and browser cookies still follow their normal scope. Every future revision requires another script/HTML/resource-domain audit. The fixed articles have no scripts, event handlers, forms or embedded media; the two executable asset patches validate family URL inputs and preserve language during internal navigation without changing article text.

Caddy permits framing only under `/wiki/*` with `X-Frame-Options: SAMEORIGIN` and `frame-ancestors 'self'`; the parent and all other routes retain `DENY`/`none`. Parent `frame-src` is same-origin, and other destinations on that origin remain unframeable. The Wiki's script/connect/font sources remain same-origin, object/frame/media sources are disabled, and its image policy lists only the seven original HTTPS image hosts plus `document-image.mubu.com`, the verified redirect destination for Mubu images. Remote article images and external downloads remain original links, so this is not an offline mirror. The frame permits forms for search, popups for external links, and downloads; it cannot navigate the top-level application.

The secondary Archive & review view retains the native article snapshots and authenticated review records. Only the authenticated archive module displays private review records; none are exported into the public Wiki package. Existing API review permissions, actor attribution, content hashes and freshness checks remain unchanged. Source content stays labelled as awaiting review; embedding it does not approve technical content or activate the SLA proposal. `/wiki/` itself contains only material already published on the original public site and does not require an employee session.

Configure private Render variables:
- `WORKOS_SUPPORT_ORG_ID`: existing Work OS organization identifier.
- `WORKOS_SUPPORT_INGEST_TOKEN`: a new random secret (32+ characters), scoped only to snapshot ingestion.
- `WORKOS_SUPPORT_USER_IDS`: explicit internal account IDs allowed to read customer support records.
- `WORKOS_SUPPORT_REVIEWER_IDS`: explicit internal account IDs allowed to record source-bound human review findings.

Existing executive accounts gain support visibility only in the configured support organization. Public Wiki material is available to authenticated employees in that organization. Reviews bind the actual authenticated account and exact content hash. They do not approve customer sending, publish knowledge, activate SLA or enable automatic answer reuse. Legacy local review records are not silently converted into new authenticated approvals.

`tools/support/publish_snapshot.py` uses an operator-owned mode-0600 JSON configuration with `origin`, `token` and `projectRoot`. Only craftos.app and the current Render hostname are accepted. Run `--dry-run` for a local schema-source/count check, `--once` for one ingestion, or without either for the single-instance 60-second loop. It reads the established SQLite database in a consistent read-only transaction and never starts another worker. It checks the DevSSD volume identity before each pass. No autostart installation is implied by launching the loop.

Ingestion is tenant-bound, bounded to 8 MiB and rejects older/conflicting timestamps, duplicate IDs and unrelated draft references. The session credential cannot ingest; the connector credential cannot read. Screens label snapshots older than 180 seconds and reject review writes until refreshed. Poller and deadline-check timestamps are separately displayed: a fresh upload does not prove the automation is running.

Production cutover must independently verify the real employee session and loaded records. Keep customer content out of GitHub and public QA artifacts. A subsequent worker migration must preserve the old database, checkpoints, existing callback tools and ambiguous-job handling, with only one active dispatcher.
